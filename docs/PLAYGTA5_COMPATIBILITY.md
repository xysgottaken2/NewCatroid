# PlayGTA5 snapshot findings and NewCatroid compatibility limits

**Research date:** 2026-10-15. This is a behavioral review of a public browser-client snapshot, not the original PlayGTA5 source repository, not an endorsement, and not a license to use or redistribute its files. The reviewed GitHub project explicitly says reuse rights are unverified and its repository has no license. No game assets, WASM module, or data mirror were copied into NewCatroid.

The public `playgta5.com` root returned HTTP 401 during this review. No credentials, authentication bypass, or access-control workaround was used. The Catroid workspace has no `game.wasm` or game data mirror, so there was no basis for claiming successful gameplay or diagnosing a specific failure inside the game engine.

## Public-client behavior verified

The archived snapshot at commit [`787e9e1946f797b2fb06f6af97cdf1f86ea611ab`](https://github.com/Adityabaskati-weeb/playgta5/tree/787e9e1946f797b2fb06f6af97cdf1f86ea611ab) was inspected read-only. The fixed-commit source links below are included so the findings can be audited; the snapshot is community-maintained and may differ from the live service.

### Startup and isolation

- `homepage.html` stops at a visible “not cross-origin isolated” message unless `crossOriginIsolated` is true. It transfers its canvas with `transferControlToOffscreen()`, then creates a top-level `Worker` for `loader.js`.
- `loader.js` creates separate `wgpu_worker.js` and `io_worker.js` workers, passes the data base URL and a bootset, fetches `game.wasm`, and instantiates the Emscripten module. Its glue tries the streaming WebAssembly path and has a download-then-compile fallback.
- The snapshot's response-header example uses `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`. NewCatroid's local server already emits the isolation headers for hosted documents; the built-in check now reports what the browser actually received.
- The browser client also uses shared WebAssembly memory/Atomics, a worker-based GPU path, AudioWorklet audio, and persistent block storage through OPFS when available. Its game glue constructs shared WebAssembly memory with an `address: 'i64'` descriptor, so a WebView that lacks the required shared Memory64 behavior will fail even if ordinary WebAssembly compilation works. The runtime probes in NewCatroid report API presence and attempt a small shared Memory64 allocation and a WebGPU adapter request; API presence alone is not proof that the complete game can run.

### Data and worker path

`io_worker.js` is a distinct browser download path, not the Catroid URL-to-file block:

1. It fetches `/data/manifest.json`, selects `bootset.json` or `bootset_low.json`, and asks for data under the page origin's `/data/` base.
2. It tries the cached compressed-batch URL `/data/batchc/<hash>.bin` and otherwise posts byte-run lists to `/data/batch` (the gzip form includes `gz=1` and manifest-version parameters).
3. Large/other files are fetched in inclusive byte ranges with `Range: bytes=start-end`; the client accepts a `206` response and has a fallback path for a server that responds `200` to a range request.
4. It streams response chunks into an append-only OPFS store and journal when the required storage APIs are available; otherwise its own source describes a bounded 48 MiB memory cache. This is why a NewCatroid `FilesUrlAction` change cannot by itself repair a browser-worker fetch or OPFS failure.
5. The snapshot sets 32 parallel range lanes and four compressed-batch lanes. NewCatroid's embedded server was corrected to let a matching bounded number of request handlers run concurrently; the client values do not promise a particular rate on Android/SAF.

The current Catroid server already has the corresponding `/data/batch` route, normal manifest/file serving, range support, and streamed large-file GETs. The range/batch request formats and hosted game files were not changed for this work.

### Browser input bridge, not game action semantics

The public page maps `KeyboardEvent.code` values into a shared 256-byte input block. Its table contains standard navigation/modifier/punctuation keys, `Digit0`–`Digit9`, `Numpad0`–`Numpad9`, `KeyA`–`KeyZ`, and `F1`–`F24`. The page deliberately passes `F5`, `F11`, and `F12` through to the browser. Its mouse bridge handles `mousemove` deltas/coordinates and mouse buttons 0–4; the internal mouse-button bit order is `[0, 2, 1, 3, 4]` for DOM `MouseEvent.button` values 0–4. In its optional flight-input convenience mapping it aliases I/K/J/L/U/O to numpad keys.

This is evidence about which browser events the page bridge accepts. It does **not** reveal the game's semantic action for each key; that behavior is inside the unavailable game module. Accordingly, NewCatroid's overlay uses neutral labels (`SPACE`, `SHIFT`, `CTRL`, `LCLICK`) and allows custom key/mouse assignment. Its default WASD, mouse movement, Space, Shift, Control and left-click controls are input events, not a verified “jump/sprint/fire” mapping. No gameplay-key claim is made.

## Worker error interpretation

The snapshot's Emscripten glue formats a worker error using `event.filename`, `event.lineno`, and `event.message`. A browser that omits those event fields can make the displayed text contain `undefined`; that explains one possible formatting artifact but does not explain the failure itself. NewCatroid now logs available worker error fields, worker `messageerror`, unhandled promise rejections, resource/HTTP failures and relevant browser capability probes. It does not ignore worker errors.

The Android activity's always-on page observer wraps page-created Worker instances. It is not injected into nested worker global scopes by default. The separate opt-in mode below adds narrow hooks to the PlayGTA5 loader's GPU and I/O workers; it does not instrument the Emscripten pthread workers.

## NewCatroid opt-in diagnostics and pipeline-mode experiment

These parameters are independent, removable, and do not modify the hosted game files:

- `?newcatroid_debug=1` adds the mobile diagnostics panel. It samples the page's displayed stage/percentage and last-change time; records engine progress messages, page/worker exceptions and unhandled rejections; observes loader/GPU/I/O worker handshakes; instruments loader WebAssembly-instantiation timing; and listens for worker console messages about WebGPU, shader/pipeline validation, formats, framebuffer/context failures, resize and worker waits. It reports page/GPU-worker heartbeat gaps and a 15-second worker-start timeout when observable. It separately records engine initialization/world-ready signals, GPU context/canvas configuration/current-texture/queue-submit milestones, CSS and backing canvas sizes, viewport dimensions, `innerWidth`/`innerHeight`, DPR and engine resize messages. A submit or first-frame signal does not prove a frame was displayed. Adapter identity/features/selected limits are shown when exposed; the page probe does not create a GPU device or WebGL context.
- In the GPU worker, the diagnostics observe `device.onuncapturederror` and error values returned by the game's existing `popErrorScope()` calls; they do not add `pushErrorScope()` calls or wrap the game renderer. Errors retain message/type, first and last timestamps, count, source kinds and nearby operations. Repeated errors are grouped without collapsing distinct sources. Bounded API context includes render/compute pipeline descriptors (shader labels, entry points, target/depth formats, vertex layouts and primitive state), bind-group layouts/resources, sampler/buffer/texture and texture-view details, render-pass attachments/load/store/clear values, pipeline/bind-group/vertex/index bindings, draw/dispatch arguments, viewport/scissor, canvas configuration, queue submissions, and selected buffer/texture writes/copies. Shader source and GPU resource contents are not exported. Hooked method calls and error events are observations, not proof that commands validated or reached the display.
- The report separately captures the original text/stack of available exceptions (including the engine's `game-crash` BroadcastChannel payload), thread/context labels, recent relevant engine messages and worker GPU-operation context. It tracks WebAssembly memory growth and logged engine allocator/arena counters without equating linear-memory capacity, allocator usage, JS heap, virtual memory, RSS or physical memory. Leaderboard assertions remain separate events. Audio diagnostics distinguish AudioContext/worklet initialization, audio-data messages, resource-fetch outcomes and `play()` attempts/rejections/autoplay state; they cannot measure audible output or the Android audio route.
- The diagnostic report can be copied or displayed in a read-only selectable text area. Export removes URL query/hash values, common credential/private-data fields, e-mail addresses, and common local paths; failed-resource reports group by resource class/status and omit request URLs/query values. The scripts do not call `fetch`, XHR, or the game's `/log` endpoint and do not set `remoteLog`/`fullConsole`; messages are collected only when the runtime emits them to the observed console/BroadcastChannel. Consequently the overlay cannot force an otherwise-silent WASM wait message to appear.
- `?newcatroid_adreno_fix=1` manually requests the snapshot's existing synchronous render-pipeline mode by setting `syncPipelines=true` on the recognized loader launch message. The reviewed snapshot's `loader.js` maps that field to `syncpipelines=1` on `wgpu_worker.js`. The report distinguishes the page request, the intercepted launch-message field and loader receipt, and the GPU-worker URL query. Fix-only mode uses a minimal loader hook to confirm URL propagation and does not activate full worker logging, adapter probing, or heartbeats. With both `newcatroid_debug=1` and `newcatroid_adreno_fix=1`, the GPU worker also reports actual synchronous versus asynchronous render/compute pipeline API call counts. These are separate observations: the URL proves option propagation, API counters prove which methods were called during that capture, and neither alone proves that the option caused a rendering outcome. Compare default and requested modes only with equivalent captures.
- The graphics parameter is deliberately manual and is not gated on GPU detection: browser adapter information can be missing or generic. It changes pipeline-compilation timing only; it does not disable rendering features or touch controls. This is an experimental alternative to the snapshot's default asynchronous pipeline creation, **not a verified Adreno/Snapdragon fix**. The option may change load-time behavior and must be tested against the target device.
- Neither parameter changes `?newcatroid_touch=1`; touch controls remain separately gated and the graphics code never reads or dispatches touch/key input.

### What the reported ~80% and GPU-wait line establish

In the reviewed snapshot, the first GPU-worker frame reports 76%. The page animates the visible bar toward the last target and may let it creep up by as much as six percentage points while waiting for the later world-ready signal; shader preparation can report a different, near-complete target. Thus a visible 80% can mean only that the first frame was reported and the world-ready event has not yet been observed by the page. It does not identify the loader, data, WASM, shader, or device state on the user's run. The actual live service was not accessible during this review and the snapshot may differ.

Likewise, a `Ready` stage, 100% progress, `gameWorldReadySignal: true`, a ready WASM instance, or a reported adapter/vendor establishes only those individual engine/browser signals. None proves a valid frame reached the compositor or that audio was audible. The capture keeps initialization, world-ready, canvas/context, queue submission, GPU validation/device-loss, and display-presentation observability separate.

The text `engine waits on the GPU worker ... readbacks waited 0 ... skipped 0 ... ring full 0 ms, fences 0 ms` shows that the named counters were zero for that reporting interval. The reviewed source does not identify those counters' exact producer or the wait predicate behind that message. It therefore does **not** prove the GPU worker is dead, prove that it is healthy, or link the wait to a black screen. The loading stall and black-screen report remain separate symptoms unless a device capture connects them.

A capture from the Galaxy S23 Ultra / Android 16 / Snapdragon 8 Gen 2 / Adreno 740 is still required. For the stall, collect the in-page report while it is at the reported percentage and compare stage/progress timestamps, worker readiness and heartbeat ages, WASM state, adapter/features/limits, shader/validation logs, and whether the GPU worker URL contained `syncpipelines=1`. For the black screen, separately confirm whether a first frame/world-ready signal occurred and inspect WebGPU context/device/pipeline errors. Compare default mode with `newcatroid_adreno_fix=1`; record whether startup, world readiness, and visible rendering change. No device reproduction or fix claim is made by source inspection or automated tests alone.

No real PlayGTA5 runtime capture is available in this change: no actual WebGPU validation message, `RuntimeError: unreachable` stack, presented frame, audible output, process-memory/OOM evidence, or causal leaderboard correlation has been observed. The error payloads in automated tests are synthetic fixtures used to verify the collector; they are not evidence about the user's device or game session. The origin of `unreachable` remains unknown until the original exception/stack and its nearby engine/worker events are captured.

## GeckoView decision

A genuine GeckoView choice is **not implemented**. The existing activity is Android `WebView`; adding a preference or “GeckoView” label without a real `GeckoRuntime`/`GeckoSession`/`GeckoView` host would not select another engine. Official Maven metadata checked on 2026-10-15 listed `158.0.20261007201254` as the latest stable GeckoView artifact, but the required Android integration, native package-size impact, compatibility with this app's `compileSdk 34`, AGP `8.6.0` and Java 11 bytecode target, same-origin isolation behavior, and target-device behavior all need validation. More importantly, the current Firefox-for-Android WebGPU implementation status lists WebGPU as disabled by default/behind a flag, while the reviewed client launches a WebGPU worker. Enabling an unsupported hidden preference would not be a safe compatibility fix.

The appropriate follow-up, if requested, is a separately packaged optional GeckoView build flavor, with explicit SDK/Java/native-size review and the same local isolation/capability tests run on the target hardware. Until that is verified, NewCatroid remains on Android WebView and reports capabilities honestly.
